Utiliser PostgreSQL plutôt que SQLite ?

exploitation base-de-donnees

Nous avons un PostgreSQL géré et sauvegardé. Le bastion peut-il l'utiliser ?

Question fréquente · 2026-11-04
Réponse
Réponse de référence

Oui, sans changer d'image : une seule variable choisit le moteur.

# SQLite (défaut) : vide, ou un chemin de fichier
ENDORIUMFORT_DB_DSN=

# PostgreSQL
ENDORIUMFORT_DB_DSN=postgresql://endoriumfort:<mot-de-passe>@db.example.com:5432/endoriumfort?sslmode=require

Le journal de démarrage confirme le choix : [config] database backend=postgresql. Si la base est injoignable, le bastion refuse de démarrer plutôt que de tourner sans comptes ni journal ; la politique de redémarrage du conteneur réessaie, ce qui règle le cas d'un PostgreSQL plus lent à démarrer.

Préparer la base

CREATE ROLE endoriumfort LOGIN PASSWORD '<mot-de-passe>';
CREATE DATABASE endoriumfort OWNER endoriumfort;

Le bastion crée ses tables au premier démarrage. Chiffrez la connexion (sslmode=require ou verify-full) dès que la base n'est pas sur le même hôte.

Migrer une installation SQLite

Le dépôt fournit scripts/migrate-sqlite-to-postgres.py, qui produit un script SQL relisible avant application :

  1. sauvegardez, puis arrêtez le bastion ;
  2. démarrez-le une fois avec le nouveau ENDORIUMFORT_DB_DSN pour créer les tables, puis arrêtez-le ;
  3. générez et appliquez les données (commandes ci-dessous) ;
  4. redémarrez le bastion avec ENDORIUMFORT_DB_DSN.
scripts/migrate-sqlite-to-postgres.py --replace /chemin/vers/endoriumfort.db > load.sql
psql "postgresql://..." -v ON_ERROR_STOP=1 -f load.sql

--replace vide les tables cibles : à n'utiliser que sur une base qui ne contient que l'amorçage du bastion, jamais sur une base en service. Gardez la même ENDORIUMFORT_VAULT_KEY : les secrets migrés sont chiffrés avec elle.

Deux précisions

  • Le journal d'audit reste un fichier sur le volume de données : gardez ce volume, et sauvegardez-le avec la base (pg_dump ou votre sauvegarde continue ne le couvrent pas).
  • Une seule instance du bastion à la fois, même avec PostgreSQL : une partie de son état vit en mémoire, et la chaîne d'audit est strictement séquentielle.
